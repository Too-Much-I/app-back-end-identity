# TMI-203 최소 정리안 Jira 설명 수정안

- 날짜: 2026-10-13 / 상태: 사용자 미리보기 승인 후 TMI-203 설명 반영·재조회 일치 확인 완료. 제목/상태 유지, 댓글 등록 없음.

## 1. 5줄 결론

1. 대상은 TMI-203 설명만이며 제목·상태·댓글은 변경하지 않는다.
2. 별도 운영 승인 저장소·갱신·외부 증명 공급 시스템을 개발 요구에서 제외한다.
3. 보존·lease·source CAS·원자성·참조 보호와 실제 회귀는 유지한다.
4. 시간 동기화·구writer 종료는 인프라/배포·복원 운영 책임으로 명시한다.
5. 이번 개정은 코드 구현·배포·활성화 완료를 뜻하지 않는다.

## 2. 사용자가 반드시 읽어야 하는 내용

앱의 독립 절대시각 오류 차단 보장은 요구하지 않는 대신 큰 시간 오차에 따른 조기 만료 위험은 운영 전제로 남는다. JWT 시간 claim 검증, capture 원자성, Billing 복원 보호까지 제거하는 변경은 아니다.

## 3. 승인 요청

아래 세 변경을 TMI-203 설명에 반영한다. 다른 내용은 유지한다. 재조회 시 예상 밖 변경이 있으면 병합 전에 다시 확인한다.

## 4. 위험·미확인

운영 시간 동기화/복원 절차는 미검증이며 공용 RuntimeEvidence 코드 정합화도 미완료다. API/body/schema/hash/index/보존기간을 바꾸지 않는다. 상대 서버 문서의 운영 전제는 별도 공유가 필요하다.

## 5. 실제 변경 문구

### A. 구현 범위의 journal/delivery 항목 교체

* journal/delivery 삭제와 floor/range 기록을 동일 transaction으로 처리한다. capturedAt+120일·source CAS/stream 교체·유효 전송 lease·bounded batch를 유지하며 충돌 시 rollback 후 다음 실행에서 새 조회한다. 별도 운영 승인/clock·writer 증명 공급 시스템은 만들지 않고 시간 동기화·구writer 종료는 아래 최소 정리 운영 경계에 따른다. capture 원자성과 기존 시간 예산 검사를 제거하는 변경은 아니다.

### B. 완료 기준 8번 추가

8. 별도 승인 저장소/API·승인 TTL/갱신/철회 worker·외부 운영증명 provider 없이 최소 정리 구조를 구성한다. 120일 경계, 유효 lease 보류, 삭제/가용성 기록 원자성, 동시 변경 rollback, unknown commit 후 새 조회, journal/snapshot 참조 보호, 폐기 stream의 종료+120일·대체 ACTIVE·bounded 정리를 검증한다. 공용 RuntimeEvidence는 capture/복구 소비처를 구분해 정합화하며 상시true 우회나 무차별 삭제로 완료 처리하지 않는다.

### C. 설명 말미에 추가

### 2026-10-13 사용자 수락 — 원천 정리 최소화

* 주기적으로 보존기간이 지난 기록을 조회하고 유효 전송 작업이면 보류한다. 원본 삭제와 재조회 불가 범위를 같은 DB transaction에 기록하고, 충돌은 rollback 후 다음 실행에서 재확인한다. 반복 오류는 장애 단위 경보 대상으로 둔다.
* 별도 승인 기록·만료·갱신 시스템, 정리마다 외부 운영증명을 요구하는 구조, 전용 clock/구writer 조사 시스템은 개발 요구에서 제외한다. 기본OFF와 명시적인 활성화 설정, DB/config preflight는 유지한다.
* 시간 동기화와 이상 대응은 인프라 운영에 맡긴다. 앱의 독립 절대시각 오류 자동 차단은 보장하지 않으며 큰 오차에 따른 조기 만료 위험이 남는다. 최초 활성화·관련 배포 완료 후·복원 시 구task/진행writer 종료·격리와 source 경계를 일반 운영 절차로 확인한다.
* 공용 RuntimeEvidence와 정리 Approval 의존성은 후속 구현에서 소비처별로 정합화한다. 구매 활성화·capture 원자성·snapshot/feed 불변식·JWT 시간 claim 검증을 일괄 제거하지 않는다.
* 원천120일/snapshot7일/operation120일/폐기stream 종료+120일, 네 recovery API·body/schema/hash/index, Billing local checkpoint/epoch와 원격ACK 부재, LC/user 인증은 유지한다. Billing 수신완료를 원본 삭제 전제로 새로 요구하지 않는다.
* 이 절은 정리용 별도 운영증명 시스템 요구를 대체한다. 실제 운영 검증·코드 완료·배포·판매·자동삭제 활성화 승인이 아니며 정리 중단을 무기한 보존 승인으로 해석하지 않는다.
